# AIC8800D80 workflow

The AIC8800 work is generator-driven. Its input is
`generators/data/aic8800-upstream.json`; regenerate with:

```bash
./scripts/generate-aic8800-upstream.sh
```

The generator updates the source-tree driver under
`drivers/net/wireless/aicsemi/` and generated review artifacts under
`generated/aic8800/`. The generator owns the driver implementation; its two
firmware-protocol source templates live in `generators/templates/aic8800/`.
Do not hand-edit generated output.

## Current capability

The native experimental fullmac path implements the observed AIC8800D80
firmware ABI instead of emulating cfg80211 state. Its boot handoff binds
bootloader ID `0x0182` on SDIO function 2, uses function 1 for the command
transport, starts the selected firmware, requests a standard MMC re-detect,
then binds runtime ID `0x0082`. It uses the standard in-band SDIO interrupt
path; the undocumented OOB/host-wake register configuration is intentionally
out of scope. It includes debug-memory commands, 1024-byte firmware block
writes, patch setup and application start; runtime reset/configuration;
station interface creation; scan results; connect/disconnect indications; key
installation; flow-controlled SDIO TX; aggregate RX; and descriptor-backed
Ethernet/802.11 conversion.

The implementation is arm64 compile-tested against local Linux v7.1.3. It has
not been exercised on a board in this repository, so documentation must
not claim successful association, traffic, regulatory behavior, suspend/resume,
or recovery until a captured hardware log establishes those results. Current
scope is a single station interface; AP/P2P, advanced PHY capability
advertisement, and Bluetooth coexistence initialization are outside it.

## Firmware and device test

No AIC firmware binary is tracked in this repository. The `aic8800_sdio`
module must be loaded after the root filesystem is available, with a verified
board-matching firmware file installed at
`/lib/firmware/aic8800d80/fmacfw_8800d80.bin` (or one of the documented
fallback names in `generators/data/aic8800-upstream.json`). Do not substitute a
random binary from another AIC8800 variant. The v7.1.3 candidate installs
`aic8800_core` and `aic8800_sdio` under `/lib/modules/7.1.3-a733/`; the latter
will first bind boot ID `c8a1:0182` and then the re-enumerated runtime ID
`c8a1:0082`.

The Orange Pi 4 Pro description uses PM1 as the active-high `WL_REG_ON` signal
(expressed as an active-low reset to `mmc-pwrseq-simple`) and the board-wired
AXP8191 BLDO5 and CLDO1 rails, both constrained to 1.8 V. PM0 is physically a
host-wake signal but is not described or used by the in-band upstream baseline.
A733 selects the PG and PM pad voltages automatically; the pinctrl drivers must
not claim the bank regulators or write the generic power-mode registers in
auto-hard mode. PMIC support and SDIO enumeration
still need a captured hardware test before this becomes an integration claim.
PB4 is not a WiFi enable; it is shared with the I2S0 clock function.

The vendor behavior reference is the Orange Pi 1.0.6 Ubuntu image with SHA-256
`0b5f284f943d7d19f7a00c317f396931b0e8e7e9d593922c342699f09ab9340b`.
Its shipped `aic8800_bsp.ko` imports `sunxi_wlan_set_power()`,
`sunxi_wlan_get_bus_index()`, and `sunxi_mmc_rescan_card()`. The observed power
path waits 50 ms after asserting PM1, requests MMC redetection, and allows 2
seconds for boot ID `c8a1:0182`; power-off waits 100 ms before redetection.
These observations constrain the standard regulator/GPIO/MMC implementation;
they do not justify importing the BSP APIs or source into this project.

## Rail ownership rule

An AXP8191 output must never be named as `mmc1`'s `vmmc-supply` or
`vqmmc-supply`. The working Orange Pi 5.15 board DTS wires **no** MMC
supplies on `sdc1` for the same reason the vendor tree always did: shared
rails and MMC power-cycle paths. PG/PM IO comes from BLDO5/CLDO1 at 1.8 V
(held always-on here because A733 pinctrl does not claim those bank
supplies), and chip enable is PM1 via `mmc-pwrseq-simple`.

A rail declared in DT without `regulator-always-on` is switched off by
`regulator_init_complete()` once its use count reaches zero.
`regulator-boot-on` does not prevent this. Because A733 pinctrl sets
`SUNXI_PINCTRL_AUTO_POWER_SWITCH`, `sunxi_pmx_request()` never claims
`vcc-pg-supply` or `vcc-pm-supply`, so no consumer holds those rails up and
BLDO5 and CLDO1 must both be `regulator-always-on`. In auto-hard mode A733
leaves `PIO_POW_MOD_SEL/CTL` under hardware ownership. The PIO register
layout is sun60iw2 TYPE_4 (`SUNXI_PINCTRL_SUN60_LAYOUT`): bank stride
`0x80` from base `0x80`, and `PIO_POW_MOD_SEL/CTL` at `0x40`/`0x48`
(vendor dump: SEL=`0x01155550`, CTL=`0x020FFC80`). Do not use D1
`NEW_REG_LAYOUT` (`0x30` stride) or A523 `ELEVEN_BANKS` (`POW_MOD@0x380`)
for the main PIO — those write the wrong physical registers (PG lives at
`0x380`, not `0x120`). Rails this port does not
model are left undeclared, which leaves them in the state the bootloader set.

To export the driver into a disposable Linux tree (the script retains its old
name for compatibility):

```bash
./scripts/export-aic8800-kernel-skeleton.sh /path/to/linux
```

The DTB and compile checks modify their target Linux tree and write local,
ignored evidence under `.tmp/validation/`:

```bash
./scripts/check-aic8800-dtb.sh /path/to/linux
./scripts/check-aic8800-skeleton-full.sh /path/to/linux
```

Those checks establish only the recorded compile/DTB result. Hardware behavior
requires a separately captured test log. The generated live report does not
promote prior JSON snapshots into a hardware-validation claim.
